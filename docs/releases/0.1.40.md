# ModulaCMS 0.1.40 : location, calendrier et catalogue

## Périmètre

- Calendrier global de location avec plusieurs plages par jour, fermetures manuelles, fuseau horaire et fournisseur de jours fériés abstrait par pays.
- Produits louables à l’heure, à la journée ou selon les deux modes, avec durées, créneaux, disponibilité, stock et contrôle des conflits.
- Validation automatique ou manuelle des locations, suivi administratif dédié, paiement sur place, marquage payé et génération de facture.
- Assurances obligatoires ou optionnelles tarifées à l’heure ou à la journée, intégrées au détail du prix, au panier, à la commande et aux documents associés.
- Parcours responsive de sélection des dates et horaires jusque dans le panier, la commande, les emails et les documents de facturation.
- Catalogue configurable par page CMS : restriction à une ou plusieurs catégories, affichage grille/liste et présentation pleine largeur d’un produit unique.
- Personnalisation des rayons des cartes, modales et navigations, appliquée aux composants publics et à l’administration.
- Ergonomie admin harmonisée : ordre d’affichage lisible, menu réduit exploitable et contrôles de paiement en ligne cohérents avec la configuration réelle du fournisseur.
- Modèle de site « Location nautique » construit sur les produits en mode location et publié dans le registre.

## Calendrier et disponibilité

- Le planning hebdomadaire accepte plusieurs plages horaires par jour et des fermetures exceptionnelles.
- Les calendriers public et admin partagent les mêmes règles métier et restent utilisables sur mobile.
- Le mode mono-journée propose des créneaux horaires ; le mode multi-jours conserve des heures de retrait et de retour compatibles avec les ouvertures.
- La disponibilité est recalculée côté serveur lors de la création de commande afin d’éviter les réservations concurrentes ou hors stock.

## Commandes, paiements et documents

- Une location peut demander une validation manuelle avant confirmation, notamment pour les paiements sur place.
- L’administration dispose d’un écran de gestion des locations, d’actions de statut et d’une action explicite pour marquer un règlement sur place comme payé.
- Les emails de location sont séparés des emails de vente et suivent les transitions de validation, confirmation, refus et annulation.
- Le prix détaille la location, les assurances, la TVA et la durée facturée ; les documents associés sont consultables depuis la fiche produit et le panier.
- Le paiement en ligne n’est proposé ni enregistrable si aucun fournisseur et aucun compte connecté valide ne sont configurés.

## Catalogue et interface

- Le composant boutique peut être attaché à une page CMS et limité à un sous-ensemble de catégories.
- Le visiteur peut basculer entre grille et liste lorsque l’option est activée ; une sélection mono-produit conserve la présentation large historique.
- Le sélecteur de catégories disparaît lorsqu’une seule catégorie est exposée et permet de revenir à l’ensemble lorsque plusieurs catégories sont disponibles.
- Les boutons, cartes produit et calendriers ont été repris pour éviter les doublons, débordements et retours intempestifs en haut de page.
- Les rayons de cartes, modales et éléments de navigation sont réglables dans le thème avec aperçu immédiat.

## Modèle nautique

Le modèle `boat-rental` est distribué exclusivement par le registre. Il n'est pas ajouté aux modèles embarqués et ne peut pas servir de fallback local. Le code de génération présent dans le dépôt sert uniquement à produire et publier son snapshot dans le registre.

Version de registre publiée : `boat-rental` v1 (`tplver_8710ab41-c22b-4802-82c8-f720122f8b26`).

## Données et migrations

- `0033_add_rental_booking_mode` : mode de réservation, durées autorisées et pas des créneaux.
- `0034_add_rental_pricing` : tarifs horaires et journaliers.
- `0035_add_rental_approval_mode` : validation automatique ou manuelle.
- `0036_add_billing_document_rental_pricing` : tarification et caractère obligatoire des assurances de location.
- `0037_add_cms_page_application_config` : configuration du composant applicatif par page CMS.

Les migrations doivent être appliquées dans l’ordre sur SQLite et D1. Les artefacts générés sont inclus dans l’archive runtime.

## Vérifications techniques

- `npx nuxt typecheck`
- suites automatisées existantes et nouveaux tests calendrier/validation location
- statut et cohérence des migrations SQLite/D1
- build Node
- build Cloudflare
- contrôle UI automatisé de non-régression
- `git diff --check`

Commandes exécutées avant publication :

```sh
npm run db:generate:internal
npx nuxt typecheck
node --experimental-strip-types --test tests/event-validation.test.mjs tests/dashboard-sql.test.mjs
node --experimental-strip-types --test tests/event-editor.test.mjs
node --test tests/event-meta.test.mjs tests/event-notifications.test.mjs tests/runtime-release-migrations.test.mjs tests/rental-approval.test.mjs tests/rental-calendar.test.mjs
node tests/floating-dropdown.mjs
npm run db:migrate:status
node ./scripts/run-platform-command.mjs server build
node ./scripts/run-platform-command.mjs cloudflare build
node tests/release-ui.mjs
git diff --check
```

Résultats : 24 tests automatisés réussis, 2 scénarios de menu flottant réussis à 390 et 1280 pixels, et 12 scénarios SSR/hydratation réussis aux mêmes largeurs. Le typecheck, le build Node, le build Cloudflare et `git diff --check` passent. Les migrations SQLite `0033` à `0037` sont appliquées et aucune migration locale n’est en attente.

Le contrôle `cms:db:d1:migrate:local` doit être lancé depuis une instance hôte Cloudflare : le dépôt runtime ne possède volontairement pas le `wrangler.jsonc` contenant le nom de sa base D1. Dans ce dépôt, la compatibilité Worker/D1 est vérifiée par le build Cloudflare, le scénario Miniflare des agrégations D1 et la présence des variantes `d1.sql` dans chaque migration moderne. Aucun déploiement ni aucune migration D1 distante n’est effectué par la procédure de publication du runtime.
